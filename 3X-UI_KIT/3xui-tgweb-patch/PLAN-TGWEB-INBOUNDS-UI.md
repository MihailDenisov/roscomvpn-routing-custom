# PLAN — TgWeb inbound presentation in 3x-ui

Date: 2026-10-07

## Context

Production TgWeb integration is working and the virtual inbound is already migrated into 3x-ui.

Current production model:

- TgWeb is represented by a normal positive-ID inbound row.
- Protocol: `tgweb`.
- The TgWeb inbound is virtual and MUST NOT become an Xray listener.
- `inbounds.port = 0` is intentional and must remain unchanged in the database.
- Public endpoint is stored in settings:
  - `publicHost = web.maicraft.tech`
  - `publicPort = 443`
- Authoritative user attachment is `client_inbounds`.
- `settings.clients` for TgWeb intentionally stays empty.
- Runtime credentials/counters live in the external TgWeb runtime and are reconciled by patched x-ui.

Observed current UI on the Inbounds page:

- Port is shown as `0`.
- Client count is shown as `0`.
- Traffic is shown as `0 B`.
- Speed is shown as `—`.

Example current row:

```text
8  Telegram WebProxy  0  tgweb  0  0 B  —
```

This does not mean the runtime is broken. It means the standard inbound table assumes an Xray-style inbound and does not yet have presentation/aggregation rules for a virtual TgWeb inbound.

## Comparison with MTProto

MTProto and TgWeb are not identical internally.

MTProto:

- is a real supported inbound;
- listens on localhost (currently `127.0.0.1:10445`);
- is exposed publicly through nginx/external proxy on port 443;
- participates in the normal inbound/statistics model.

TgWeb:

- is a virtual control-plane inbound;
- has no Xray listener;
- therefore stores `port=0`;
- public traffic enters through nginx and the separate `tgwebproxy` runtime;
- users are attached through `client_inbounds`;
- statistics must be read/aggregated from TgWeb accounting, not Xray stats.

Do NOT redesign TgWeb to imitate MTProto internally just to satisfy the UI.

## Goal

Make the TgWeb row on the 3x-ui Inbounds page look natural and useful while preserving the existing architecture and isolation.

Target example:

```text
8  Telegram WebProxy  443  tgweb  6  <TgWeb traffic>  —
```

The exact visual formatting may use `443`, `443 external`, or equivalent wording if that improves clarity.

## Required changes

### 1. Public port display

For ordinary protocols, keep current behavior.

For `protocol=tgweb`:

- leave database field `port=0`;
- display `settings.publicPort` in the Inbounds table;
- use `443` for the current production inbound.

Do NOT write `443` into `inbounds.port`.

Reason: `port=0` is an architectural guard indicating that TgWeb is not an Xray listener.

### 2. Client count

The standard page must not derive TgWeb client count from:

```text
settings.clients.length
```

because TgWeb intentionally keeps:

```json
{"clients":[]}
```

For TgWeb, count attached clients using the authoritative relation:

```text
client_inbounds
```

For the current production state the expected count is 6.

The implementation should respect only the selected TgWeb inbound ID rather than counting all global clients.

### 3. Traffic

Ordinary inbound traffic remains sourced from existing Xray statistics.

For TgWeb, traffic must come from the already implemented TgWeb accounting/runtime counters.

The value should be consistent with the same current-epoch / baseline semantics used for shared quota accounting. Do not simply sum lifetime runtime counters if that would make the Inbounds page disagree with quota/reset semantics.

Desired result:

- show aggregate TgWeb upload/download or combined traffic using the existing table convention;
- no double counting with VPN/Xray traffic;
- no mutation of runtime counters;
- read-only statistics path.

### 4. Speed

Preferred options, in order:

1. If there is already a safe runtime delta/rate mechanism, expose TgWeb upload/download rate using it.
2. Otherwise leave speed as `—` for this iteration.

Do not add a fragile polling subsystem solely to populate the speed column.

### 5. TgWeb settings presentation

The settings/details UI should not present `port=0` as if it were the user's network endpoint.

For TgWeb show the logical/public endpoint, for example:

```text
Protocol: Telegram WebProxy
Public host: web.maicraft.tech
Public port: 443
```

Internal `port=0` may remain in the raw data/model but should not be emphasized as the usable endpoint.

Investigate the currently displayed/generated tag:

```text
in-0-tcp
```

The intended TgWeb identity is `tgweb-web`.

Determine whether `in-0-tcp` is:

- actually stored in the DB, or
- only generated by frontend serialization/default logic.

Do not rewrite production data until the source is understood.

## Rebuild/deployment implications

This work affects the built 3x-ui frontend and may also require a small backend API/statistics adapter.

Therefore a new x-ui binary build is expected.

This is NOT a repeat of the previous full migration rollout.

Not required:

- no database migration;
- no `migrate_legacy_v2.py --apply`;
- no nginx changes;
- no tgwebproxy changes;
- no runtime secret rotation;
- no legacy reconciler re-enable;
- no recreation of the TgWeb inbound.

Expected workflow:

```text
current main
  ↓
dedicated TgWeb Inbounds UI/stats patch
  ↓
frontend/backend tests
  ↓
make build
  ↓
new x-ui binary
  ↓
review diff + binary/hash
  ↓
backup current production binary
  ↓
atomic binary replacement + restart x-ui
  ↓
focused smoke test
```

Production deployment must remain a separate explicit approval step.

## Development plan

1. Start from current `main`.
2. Create a dedicated branch, for example:
   `fix/tgweb-inbound-stats-ui`.
3. Locate the Inbounds table component and the backend/API fields that feed:
   - port;
   - client count;
   - traffic;
   - speed;
   - settings/details.
4. Add protocol-aware behavior only for `tgweb`.
5. Reuse existing TgWeb manager/accounting methods where possible instead of creating another runtime client.
6. Keep TgWeb excluded from Xray config generation.
7. Add focused regression tests.
8. Run frontend tests/typecheck/lint/format.
9. Run relevant Go tests.
10. Run full `make build`.
11. Record binary SHA256 and changed files.
12. Review final diff before any production deployment.

## Required tests

At minimum verify:

- TgWeb DB `port` remains 0.
- Inbounds UI displays `settings.publicPort`.
- TgWeb client count is derived from `client_inbounds`.
- Detached client reduces TgWeb count.
- Reattach restores TgWeb count.
- Global client disable does not corrupt attachment count semantics.
- TgWeb traffic is populated from TgWeb accounting.
- Traffic reset/current epoch semantics are respected.
- TgWeb remains absent from generated Xray config.
- Existing non-TgWeb inbound rows remain unchanged.
- MTProto behavior remains unchanged.
- TgWeb runtime/API outage does not break the whole Inbounds page; it should degrade safely.
- No TgWeb secret is returned through generic inbound/list APIs.

## Production smoke after approved deployment

After installing the newly built binary:

1. Verify x-ui starts cleanly.
2. Verify Xray config contains no TgWeb entry.
3. Verify VPN sidecars and existing 42 VPN attachments are unchanged.
4. Verify TgWeb runtime users/secrets/counters are unchanged.
5. Open Inbounds page and verify:
   - TgWeb port shows 443/public endpoint;
   - client count shows current attached count;
   - traffic is non-zero when runtime counters are non-zero;
   - speed is either valid or intentionally `—`.
6. Detach one safe test client from TgWeb and verify client count decrements without affecting VPN attachments.
7. Reattach and verify count restores.
8. Verify subscription page and TgWeb connection continue working.

## Explicit non-goals

Do NOT:

- change TgWeb to a real Xray listener;
- change DB port from 0 to 443;
- repopulate `settings.clients` for TgWeb;
- duplicate `client_inbounds` into another attachment table;
- reset runtime counters;
- modify nginx routing;
- modify the already successful production migration;
- re-enable the legacy reconciler.
